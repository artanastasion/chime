Независимый вариант для обсуждения

Сценарий: отправитель выбирает трек и получает ссылку. Получатель открывает ссылку, при необходимости указывает музыкальные предпочтения, а Chime подбирает другую композицию со схожей эмоционально-акустической характеристикой. Ссылка отправляется через внешний мессенджер.

Важно: все элементы, помеченные как «новые», являются проектным предложением. Обе исходные схемы Chime сохранены ниже без функциональных изменений.

1. Архитектура Translate

От клиента до результатов: новые сервисы выделены персиковым, существующие — синим, аналитика — фиолетовым. Пунктир — асинхронные или логические связи.

01 · Отправка

FastAPI сохраняет ссылку с token_hash, ID исходного трека, отправителем и сроком действия. Внешний чат не нужен.

02 · Получатель

При переходе по ссылке API проверяет токен, срок действия, публикацию исходного трека; получатель авторизуется и может выбрать жанры без длительной истории.

03 · Подбор

Ranker сравнивает заранее рассчитанные характеристики музыкального настроения и предпочтения адресата. Возвращает трек, оценку и информацию для объяснения.

04 · События и метрики

Выдача ссылки, открытие, выбор и прослушивание результата попадают в поток событий и ClickHouse. Сначала полезная функция, затем аналитика.

2. Новые сущности и связи PostgreSQL

Показаны только таблицы, затронутые функцией. Полная оригинальная схема PostgreSQL находится ниже.

Новая сущность / хранилищеНазначение и ограничения
track_featuresПредрассчитанные признаки целого трека (темп, энергия, valence, embedding), версия извлечения и статус готовности. PK одновременно FK на tracks.
audio_analysis_jobsИдемпотентная обработка конкретного media_assets.asset_id с версией модели, retry и ошибками.
user_taste_preferencesЯвные пользовательские жанровые предпочтения. Составной PK (user_id, genre_code), ограничение веса 0…1.
translation_linksСсылка на исходный трек. Храним только хеш случайного токена, срок действия и отзыв.
translation_resultsПодобранный трек для авторизованного получателя, связь с ссылкой, score и версия модели. FK на users и tracks.

3. Что изменено и почему

Общая модель каталога

tracks, media_assets, RustFS остаются неизменными; аудио не копируется ради новой функции.

Независимость от истории

user_taste_preferences хранит явный выбор жанров/весов. Достаточно заполнить при первом использовании; история может улучшать подбор позднее, но не обязательна.

Нет социального бэкенда

translation_links реализует внешнее распространение по ссылке. Не создаём друзей, чаты, переписку и уведомления.

Сначала предрасчёт

Audio Analysis Worker вызывается при появлении новой доступной версии аудио, а не при открытии каждой ссылки.

Прозрачная оценка

translation_results фиксирует конкретный результат и версию признаков; качество можно оценивать отдельно от рекламной идеи «одинаковых эмоций».

Безопасность

Храним hash токена, срок действия, отзыв ссылки; API ограничивает частоту запросов и не раскрывает профиль получателя отправителю.

4. Исходная модель PostgreSQL (без изменений)

7 таблиц схемы public (база music_platform, миграции Alembic). Связи нарисованы от внешнего ключа к первичному с политикой ON DELETE. Бинарное содержимое хранится в RustFS; в PostgreSQL — только регистрация объекта и связь актива с треком или релизом.

5. Исходные потоки Chime (без изменений)

Каждый сервис, топик, Kafka-таблица, материализованное представление, таблица и витрина ClickHouse — отдельная нода; стрелки показывают направление движения данных. Пунктир — чтение и служебные шаги. Все пользовательские действия проходят через HTTP API приложения.

колесо — масштаб · перетаскивание — перемещение · наведение — связи
  • HTTP-запросы клиентов
  • запись/чтение OLTP (SQL, S3 API)
  • бинарники: загрузка и Range-стриминг
  • CDC: изменения строк PostgreSQL
  • события: access-лог и телеметрия
  • трансформация внутри ClickHouse (MV)
  • битые сообщения → dead-letter
  • чтение: дашборды, сверка, обслуживание
  • bootstrap: одноразовые init-шаги
